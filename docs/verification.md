## 手机、平板尺寸预览修复

问题在工作台的「手机 · 390 px」「平板 · 768 px」宽度选项下复现：网页响应 `resize` 事件并重新加载后，截图程序继续使用旧文档的执行上下文，报 `Cannot find context with specified id`。旧版失败证据保存在 `artifacts/preview-regression-before.json`。

修复后会在调整尺寸后重新等待文档；若准备或截图期间发生重载，会重新读取页面，最多尝试 3 次。截图后再次确认文档并更新标题、网址。恢复原页面时也会等待短暂稳定后恢复滚动位置，取消和失败路径仍会解除截图连接。

新增的 6 个引擎回归场景：

- 390 / 768 px：网址页面延迟重载后截图成功，像素与尺寸正确，临时标签页关闭。
- 390 / 768 px：现有标签页即时重载后 2 倍截图成功，原始尺寸、像素比和滚动位置恢复。
- 恢复桌面宽度时延迟重载，仍能恢复原滚动位置。
- 持续重载时有限退出并给出中文提示，释放截图任务，下一次预览可以继续。

本次验证结果：23 项单元与导入测试、16 个引擎场景、16 个工作台场景全部通过。另测桌面 / 手机 / 平板工作台、网址 / 本地 HTML、390 / 768 px、1 / 2 / 3 倍共 36 组组合，图片非空、尺寸正确、预览可见且无横向溢出，未出现 UI 或脚本错误。这些是桌面 Chromium 中的宽度及工作台尺寸验证，不代表真实移动设备可安装 Chrome 扩展。

最新证据：`artifacts/engine-e2e.json`、`artifacts/ui-test-results.json`、`artifacts/preset-diagnostic.json`。安装目录及 ZIP 通过 `npm run build` 重新生成；已有用户需要在扩展管理页刷新拾页，再刷新工作台。

## 1.1.0：自定义宽度、来源重置和完整滚动导出

复现发现，普通长网页的截图高度正确，但固定视口内的主滚动容器并未包含在文档高度中，导致所有格式都只收到一屏图片。另一个独立问题是超长 WebP：Chromium 对超出 16,383 像素的画布可能输出成功但截短图片。两类问题分别在捕获和编码阶段修复。

内部滚动捕获会选出主要正文区域，逐段滚动并等待可见内容绘制，用实际滚动位置消除最后一段的重叠，再拼接完整 PNG。这样也能处理只渲染可见内容的虚拟列表。导出器以同一张完整截图生成 JPG、WebP 和 PDF；超限 WebP 按比例缩小并检查实际编码尺寸。取消、失败和成功都会恢复临时样式、滚动位置、原始视口和像素比。

本次验证：

| --- | --- | --- |
| `npm test` | 25 项 | 参数、自定义宽度、WebP 尺寸、PDF 切片和 HTML 导入 |
| `npm run test:engine` | 16 个场景 | 原有捕获、尺寸切换重载及取消回归 |

全格式检查逐像素核对顶部、中间和末尾色带出现一次且间距正确，并确认分页 PDF 的图片行完整覆盖原始截图。滚动专项另外核对 180 行虚拟列表逐行完整，6000 像素主区域输出高度正确，2 倍结果为 1136 × 12000 像素。所有源页面的滚动位置及原始 style 属性均严格恢复。旧版在同一滚动专项中 5 项失败、2 项通过，旧证据保留供对照。

吸顶元素专项确认：长正文和两个不同位置的 sticky 标题都保留，标题各出现一次，临时取消吸附的样式完整恢复。全格式测试使用与发布构建相同的压缩打包设置，核验注入页面的函数在构建后仍可正常执行。

私有在线对话没有在测试浏览器中取得登录后的页面，因此这里验证的是相同的固定视口、正文内部滚动和虚拟渲染结构，没有宣称已通过该私有会话实测。检测针对单个主要滚动区域；多个小面板、跨域 iframe、被外层裁切而不能滚动到末尾的特殊容器仍不保证完整捕获。检测到长度变化、尺寸过大或不能继续滚动时会明确报错，避免把不完整结果当作成功导出。
